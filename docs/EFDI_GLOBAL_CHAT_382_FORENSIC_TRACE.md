## 4. Origin of 382

### WHERE DID 382 FIRST APPEAR?

**The number 382 first appeared directly from PostgreSQL as the return value of the SQL query.**

It was **NOT** an LLM hallucination, **NOT** a transformation bug in Python, and **NOT** a value hallucinated by the agent.

### Forensic Breakdown of the Database State

In PostgreSQL (`EFDI` database, table `documents`):
```sql
SELECT status, COUNT(*) 
FROM documents 
WHERE is_deleted = false 
GROUP BY status;
```

**Actual database count breakdown by document lifecycle status:**

| Status | Count |
|---|---|
| **UPLOADED** | **382** |
| VALIDATED | 444 |
| OCR_COMPLETED | 97 |
| EXTRACTED | 27 |
| REJECTED | 8 |
| PENDING_APPROVAL | 6 |
| APPROVED | 4 |
| **Total Active Documents (`is_deleted = false`)** | **968** |
| Deleted Documents (`is_deleted = true`) | 59 |
| **Total Physical Rows in `documents`** | **1,027** |

### Root Cause of the 382 Output

1. The `documents` table contains a column named `status` with enum-like lifecycle values:
   `UPLOADED`, `OCR_COMPLETED`, `EXTRACTED`, `VALIDATED`, `PENDING_APPROVAL`, `APPROVED`, `REJECTED`.
2. When the user asked `"how many documents were uploaded"`, the SQL-generation LLM read the schema definition:
   `status (str: UPLOADED, OCR_COMPLETED, EXTRACTED, VALIDATED, APPROVED, REJECTED)`
3. The SQL-generating model interpreted `"uploaded"` as a condition on `status` rather than counting all documents ever ingested.
4. Consequently, it generated `WHERE status = 'UPLOADED'`.
5. In EFDI, documents only remain in status `UPLOADED` until they undergo OCR and downstream processing. Exactly **382 documents** are currently in that initial staging state without further processing.
6. The query accurately counted documents in the `UPLOADED` state, returning **382**.

## 9. Why the Answer Changed

| Property | First Query ("how many documents were uploaded") | Verification Query ("verify your output...") |
|---|---|---|
| **User Prompt** | `"how many documents were uploaded"` | `"verify your output. Is the number of documents 382?"` |
| **Tool Selected** | `database_query_tool` | `database_query_tool` |
| **SQL Filter Generated** | `WHERE status = 'UPLOADED' AND is_deleted = FALSE` | `WHERE is_deleted = FALSE` |
| **Target Metric** | Documents currently in the `UPLOADED` lifecycle state | All non-deleted documents in the entire system |
| **PostgreSQL Result** | **382** | **968** |
| **Final Answer** | **382** | **968** |

### Concrete Reason:
In the first query, the word **"uploaded"** matched the schema column value `status = 'UPLOADED'`. The SQL-generating LLM filtered exclusively for documents in that specific staging state (`382`).

In the second query, the user challenged the total number of documents (`"Is the number of documents 382?"`). The SQL-generating LLM removed the `status = 'UPLOADED'` filter and counted all active records in `documents` (`WHERE is_deleted = false`), which returned **968**.
