## 11. Net / VAT / Gross Trace

Tracing document financial totals:

1. **True Arithmetic Values on Document:**
   $$\text{Net Amount} = 5\,640.17$$
   $$\text{Tax Amount (10\% VAT)} = 564.02$$
   $$\text{Invoice Amount (Gross Total)} = 6\,204.19$$
   $$\text{Check: } 5\,640.17 + 564.02 = 6\,204.19 \quad (5\,640.17 \times 1.10 = 6\,204.187 \approx 6\,204.19)$$
2. **Raw OCR Output (EasyOCR):**
   * Summary line 1: `10* 540,17 564 07 204 19`
   * Summary line 2: `Total 640,17 564,02 204,19`
   *(Leading digits $5$ and $6$ were truncated or segmented away by EasyOCR: $5\,640,17 \to 640,17$; $6\,204,19 \to 204,19$).*
3. **Rule-Based Extraction (Table Summation Fallback):**
   * Summed line items in table data:
     $$\text{Line Items Net Sum} = 627.00 + 188.75 + 400.00 + 394.67 + 109.95 + 79.80 + 840.00 = 2\,640.17$$
     $$\text{Line Items Gross Sum} = 689.70 + 207.63 + 440.00 + 1534.14 + 1220.95 + 187.78 + 924.00 = 5\,204.20$$
     $$\text{Derived Tax Amount} = 5\,204.20 - 2\,640.17 = 2\,564.03$$
4. **Mistral Reasoning (`open-mistral-nemo`):**
   * Mistral saw the OCR text `5 5 640,17` and `6 204,19`, but without aligned column headers:
     * Assigned `invoice_amount = 5640.17` (selected Net as Total).
     * Assigned `tax_amount = 620.19` (selected Gross as Tax).
     * Computed `net_amount = 5019.98` ($5640.17 - 620.19$).

## 16. Primary Root Causes

1. **HTTP 429 API Rate Limit / Model Tier Restriction Triggering Silent Fallback (Primary Operational Cause):**
   `EXTRACTION_LLM_MODEL=mistral-small-2603` is throttled on the active API tier. When it fails with HTTP 429, the system silently falls back to `RuleBasedExtractor`, which extracts only 4 fields.
2. **Severe Schema Inflation with Non-Document Metadata (Primary Architectural Cause):**
   14 of the 25 fields in `NPO` (`document_id`, `company_code`, `location_code`, `vertical_code`, `fiscal_year`, `barcode`, `processing_status`, `validation_status`, `cost_center`, `department`, `vendor_code`, `document_category`, etc.) are **internal system/ERP metadata fields**, not physical fields printed on vendor invoices. A 100% perfect extractor can only ever find at most 10–11 fields on a real invoice image.
3. **Rigid Regex Label Matching in `RuleBasedExtractor` (Primary Fallback Cause):**
   `RuleBasedExtractor` expects `"Invoice Date"` (document has `"Date Of issue"`), `"Vendor Name"` (document has `"Seller"`), and `"Customer Name"` (document has `"Client"`). When the LLM falls back to rule-based, all header entity fields evaluate to `not_found`.
