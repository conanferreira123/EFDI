## 1. Executive Summary

This forensic audit investigates whether the EFDI codebase already contains any function, component, or pipeline stage that parses, transforms, groups, or normalizes `raw_blocks` from OCR into a structured or layout-aware representation suitable for an LLM-based extractor.

### Key Forensic Findings:
1. **`raw_blocks` is Persisted but Disconnected from Extraction:** `raw_blocks` is generated by OCR engines (`PaddleOCREngine` / `EasyOCREngine`), assembled into a Python `list[dict]` in `OCRService.run_ocr`, and stored as a PostgreSQL `JSONB` column in `ocr_results`. When retrieved by SQLAlchemy, it deserializes back into a standard Python `list[dict]`. However, `ExtractionService.extract()` queries `ocr_result` and passes **only `ocr_result.full_text`** to `ExtractionEngine.extract()`. `raw_blocks` is **not passed downstream to extraction**.
2. **Upstream Table & Layout Processing Exists (OCR-only):** The OCR layer contains two production components:
   - `app.ocr.layout.order_blocks_spatially`: Uses bounding boxes to reorder blocks across 3 vertical bands (top metadata, 2-column party info, body/table) to produce a coherent reading order for `full_text`.
   - `app.ocr.table_reconstruction.TableReconstructor`: Groups blocks geometrically into column intervals and line-item rows, producing `ReconstructedTable` and `StructuredLineItem` objects.
   - *However*, these are consumed strictly within `OCRService` and `app/routers/ocr.py` for OCR quality scoring and API inspection. **Their output is never passed to ExtractionService or any extraction engine.**
3. **Existing `LLMBasedExtractor` is 100% Plain-Text:** `app.extraction.llm_extractor.LLMBasedExtractor` receives only `text: str` and `document_type: str`. Its prompt format is strictly `DOCUMENT OCR TEXT:\n"""\n{text}\n"""`. It has no knowledge of `raw_blocks`, bounding boxes, coordinates, page dimensions, or table structures.
4. **No Dedicated Raw-Blocks-to-LLM Adapter Exists:** There is no function in the codebase that transforms multi-page `raw_blocks` into an LLM-ready layout representation (e.g., spatial markdown, structured JSON context, or layout-aware key-value grids).

## 5. Does a raw_blocks Parser Already Exist?

**Core Question:** *"Does the current EFDI codebase contain an existing production function that takes raw_blocks and converts it into a structured representation suitable for downstream document extraction or LLM consumption?"*

### Classification of Candidates:

1. **`TableReconstructor` (`backend/app/ocr/table_reconstruction.py`)**
   - **Classification:** `2. EXISTING BUT REQUIRES ADAPTATION`
   - **What it does:** Takes `raw_blocks` (for page 0), finds column headers, derives `x_min`/`x_max` intervals, clusters lines by `y_tolerance=16.0px`, merges multiline descriptions, and returns `ReconstructedTable` with `StructuredLineItem` objects.
   - **Why it is not directly usable as-is for an LLM extractor:**
     - It only extracts table line items; it ignores document headers, party blocks (Seller/Buyer), key-value metadata pairs, and tax summaries.
     - It operates on a single page (`raw_blocks[0]`), not multi-page structures.
     - It outputs internal dataclasses, not an LLM prompt format or serialized JSON context.
     - It is currently wired only to OCR validation and OCR API responses, completely disconnected from `ExtractionService`.

2. **`order_blocks_spatially` (`backend/app/ocr/layout.py`)**
   - **Classification:** `2. EXISTING BUT REQUIRES ADAPTATION`
   - **What it does:** Segments blocks into top metadata, two-column party details (Seller left, Buyer right), and body/table bands, reordering them sequentially.
   - **Why it is not directly usable as-is for an LLM extractor:**
     - Its output is a reordered list of `OCRTextBlock` which is immediately concatenated into a flat 1D string (`full_text`). All 2D bounding boxes and column boundaries are lost during string join.

3. **`normalize_table_data` (`backend/app/ocr/normalization.py`)**
   - **Classification:** `2. EXISTING BUT REQUIRES ADAPTATION`
   - **What it does:** Cleans and parses numeric quantities, currency amounts, dates, and units from `ReconstructedTable`.
   - **Why it is not directly usable as-is for an LLM extractor:**
     - It depends on `ReconstructedTable` as input, not raw blocks directly.

4. **Dedicated Raw-Blocks-to-LLM Context Builder / Layout Adapter**
   - **Classification:** `4. DOES NOT EXIST`
   - There is **no function** in the codebase that iterates through multi-page `raw_blocks` and formats it into a layout-aware representation (such as Markdown tables, 2D spatial text grids, or structured JSON block hierarchies) for LLM consumption.

## 6. Existing Layout Processing

Located in `backend/app/ocr/layout.py`:
- **Function:** `order_blocks_spatially(blocks: List[OCRTextBlock], page_width: float, page_height: float) -> List[OCRTextBlock]`
- **Input:** List of `OCRTextBlock` objects directly from OCR engine inference.
- **Operation:**
  1. Computes polygon bounds `(min_x, min_y, max_x, max_y, cx, cy)`.
  2. Detects table start `table_y_start` via keywords (`ITEMS`, `DESCRIPTION`, `QTY`, `NET PRICE`).
  3. Detects party region start `top_meta_end_y` via keywords (`seller`, `client`, `buyer`, `vendor`, `sold by`, `ship to`).
  4. Splits into 3 bands:
     - Band 1 (Top Metadata): Ordered line-by-line (`cy / 15.0`, then `min_x`).
     - Band 2 (Party Details): Split at `mid_x = page_width * 0.5`. Left column (Seller) sorted top-to-bottom; Right column (Buyer) sorted top-to-bottom.
     - Band 3 (Body & Table): Ordered line-by-line (`cy / 12.0`, then `min_x`).
- **Output:** A flattened `List[OCRTextBlock]` in logical reading order.
- **Persistence:** This list is used to construct `OCRResultData.pages[i].full_text`. The spatial coordinates themselves are preserved only in `raw_blocks`.
- **Extraction Availability:** `ExtractionService` receives the concatenated text result (`full_text`), but not the band metadata or coordinate annotations.

## 7. Existing Table Reconstruction

Located in `backend/app/ocr/table_reconstruction.py`:
- **Class:** `TableReconstructor`, Function: `reconstruct_table(blocks, page_width, page_height) -> ReconstructedTable`
- **Input:** Accepts raw block dictionaries `{"text": ..., "confidence": ..., "bounding_box": ...}` or `OCRTextBlock` instances.
- **Output Dataclass:** `ReconstructedTable`
  - `headers: List[str]` (e.g. `["description", "quantity", "unit_price", "net_amount", "vat_rate", "gross_amount"]`)
  - `columns: Dict[str, Dict[str, float]]` (stores `x_min`, `x_max`, `cx`, `header_text` per column)
  - `line_items: List[StructuredLineItem]` (each item contains `item_number`, `description`, `quantity`, `unit`, `unit_price`, `net_amount`, `vat_rate`, `gross_amount`, `confidence`, `raw_blocks`)
  - `table_region: Dict[str, float]` (`top`, `bottom`)
  - `summary_blocks_count: int`
- **Properties:**
  - **Deterministic:** Yes, relies entirely on geometric clustering and keyword matching.
  - **Preserves Coordinates:** Yes, each `StructuredLineItem` retains the list of constituent `raw_blocks`.
  - **Preserves Confidence:** Yes, averages block confidences for each line item.
  - **Multiline Description Merging:** Yes, lines lacking numeric quantity/price that fall under an active item are merged into `current_item.description`.
- **Current Consumer:** Called strictly in `OCRService.run_ocr` (for logging OCR completion audit events) and `app/routers/ocr.py` (for API response field `table_data`). **Never called by extraction.**

## 10. LLMBasedExtractor Analysis

Located in `backend/app/extraction/llm_extractor.py`:

### Detailed Breakdown:
- **Input Parameters:** `extract(self, text: str, document_type: str) -> ExtractionResultData`
- **Dynamic Schema Generation:** Calls `build_dynamic_extraction_model(document_type)` (`app/extraction/llm_schema.py`) which builds a Pydantic model at runtime containing every field defined in `field_schemas.py` for that document type. Each field is typed as `Optional[LLMFieldItem]` (`value: str`, `confidence: float`, `source_quote: str`).
- **Prompt Construction (`backend/app/extraction/llm_extractor.py`, lines 101–110):**
  ```python
  system_prompt = (
      f"You are an enterprise financial document extraction model.\n"
      f"Extract all schema fields for document type '{document_type}' from the provided OCR text.\n"
      f"For every field found, provide the extracted value, a confidence score between 0.0 and 1.0, "
      f"and the exact verbatim text snippet (source_quote) from the document as proof.\n"
      f"If a field is not present in the document text, return null for its value."
  )
  user_prompt = f"DOCUMENT OCR TEXT:\n\"\"\"\n{text}\n\"\"\""
  ```
- **Payload Sent to LLM (`_call_llm_api`, lines 43–58):**
  - Sends OpenAI-compatible Chat Completion request with `response_format: {"type": "json_schema", "json_schema": {...}}` derived from the Pydantic schema.
- **Output Handling:** Validates response via `DynamicModel.model_validate(raw_response)`, then runs `normalize_date()` and `normalize_amount()` on candidate strings.
- **CRITICAL FACT:** `LLMBasedExtractor` receives **zero layout data**, **zero bounding boxes**, **zero coordinates**, and **zero table structures**. It is purely a plain-text prompt completion engine.

## 17. Exact Answers to the 10 Final Questions

### 1. Is `raw_blocks` currently parsed anywhere?
**YES (in OCR layer only).** `raw_blocks[0]` is parsed by `app.ocr.table_reconstruction.TableReconstructor` inside `OCRService.run_ocr` and `app/routers/ocr.py`. It is **never parsed in or for extraction**.

### 2. Is `raw_blocks` currently transformed into a structured representation?
**YES (in OCR layer only).** `TableReconstructor.reconstruct()` transforms `raw_blocks` into `ReconstructedTable` and `StructuredLineItem` objects with column bounds and line rows. However, this structured output is used only for OCR quality scoring and API inspection.

### 3. Is `raw_blocks` currently transformed into an LLM-friendly representation?
**NO.** There is no serializer, adapter, or formatter in the codebase that transforms `raw_blocks` into an LLM-friendly representation (such as Markdown grids, spatial text tables, or structured JSON hierarchies).

### 4. Does the current `LLMBasedExtractor` receive `raw_blocks`?
**NO.** `LLMBasedExtractor.extract(text: str, document_type: str)` receives only `full_text` and `document_type`. `raw_blocks` is not passed to it.

### 5. Does the current `RuleBasedExtractor` receive `raw_blocks`?
**NO.** `RuleBasedExtractor.extract(text: str, document_type: str)` receives only `full_text` and `document_type`.

### 6. Does table reconstruction already process `raw_blocks`?
**YES.** `app.ocr.table_reconstruction.reconstruct_table(blocks, page_width, page_height)` directly consumes raw block dictionaries and performs geometric column derivation and row clustering.

### 7. Does extraction consume table reconstruction output?
**NO.** `ExtractionService` does not import or call `reconstruct_table`, nor does it receive `table_data` from OCR.

### 8. Is there an existing reusable function we should use for an eventual LLM extractor?
**YES (partially).** 
- `app.ocr.table_reconstruction.reconstruct_table` and `app.ocr.normalization.normalize_table_data` can be directly reused to provide structured line-item tables.
- However, an adapter function is still needed to serialize `ReconstructedTable` and multi-page block headers into prompt-ready text/JSON for the LLM.

### 9. If no such function exists, where would the smallest integration point logically be?
The smallest and cleanest integration point is:
1. An adapter module: `app/extraction/layout_adapter.py` containing a function `format_raw_blocks_for_llm(raw_blocks: list[dict], table_data: dict | None = None) -> str`.
2. Connecting it inside `app/extraction/llm_extractor.py` to inject the formatted layout context into `user_prompt`.

### 10. What is the minimum architectural change required to make `raw_blocks` available to the LLM extractor?
The minimum architectural change requires:
1. **Interface Update (`app/extraction/base.py`):** Update `ExtractionEngine.extract(self, text: str, document_type: str, raw_blocks: list[dict] | None = None)`.
2. **Service Update (`app/services/extraction_service.py`):** Pass `raw_blocks=ocr_result.raw_blocks` from `ExtractionService.extract()`.
3. **Engine Update (`app/extraction/llm_extractor.py`):** Accept `raw_blocks` in `LLMBasedExtractor.extract()` and format it into the prompt.
4. **Database & OCR:** **Zero changes needed.** `raw_blocks` is already persisted in `ocr_results`.

## 18. Final Verdict

1. **State of the Codebase:** The EFDI backend already possesses the foundational data (`raw_blocks` in PostgreSQL `JSONB`) and the geometric parsing primitives (`TableReconstructor` and `order_blocks_spatially` in `app/ocr/`).
2. **The Disconnect:** The extraction subsystem (`ExtractionService`, `RuleBasedExtractor`, `LLMBasedExtractor`) was constructed with a strictly 1D text-only interface (`extract(text, document_type)`), causing all bounding-box and table evidence to be discarded at the boundary between OCR and extraction.
3. **Path Forward for LLM Extraction:** When approved to implement an LLM layout extractor, no database migrations or OCR modifications will be necessary. The task will strictly consist of updating the `ExtractionEngine` interface signature, passing `ocr_result.raw_blocks` from `ExtractionService`, and adding a layout serializer to feed structured block/table context into the LLM prompt.
