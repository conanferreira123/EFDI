Step 3 — Review and Configure the .env  File
What: Open efdi/.env  in any text editor and check the values.
Why: The docker-compose.yml  reads this file to configure all three containers. If
POSTGRES_PASSWORD  or SECRET_KEY  is missing or wrong, docker compose up  will fail
immediately with a clear error (the compose file uses :?  syntax that enforces these are
set).
The .env  file that ships in the zip is already filled with working defaults:
Things you may need to change:

What is stub  OCR? The backend has a stub OCR engine that returns placeholder text
immediately without running any ML model. It is useful for testing the UI and workflow
without waiting for a real OCR model to download. All pipeline stages (classification,
extraction, validation, approval) work correctly in stub mode — you just get fake text
instead of real extracted content.
Step 4 — Build and Start All Services
What: Run one command from inside the efdi/  directory.
Why: docker compose up --build  reads docker-compose.yml  and .env , builds the
backend and frontend Docker images from their respective Dockerfile s, pulls the
PostgreSQL 16 Alpine image, and starts all three containers in dependency order (Postgres
first → backend → frontend).
What happens during the build (first run only):

Why does torch install from a special URL? The default PyPI torch  wheel links
against NVIDIA CUDA libraries ( libcudart.so , libcublasLt.so ). On a machine
without an NVIDIA GPU and drivers, import torch  crashes at import time — even if
you pass gpu=False . The CPU-only wheel from
https://download.pytorch.org/whl/cpu  is ~190 MB instead of several GB and
imports cleanly on any machine. The Dockerfile handles this automatically.
Subsequent starts (after the first build) are fast — Docker reuses the cached image
layers and only rebuilds stages where source files changed.

What is Alembic doing? The backend's Docker CMD  runs alembic upgrade head  before
starting Gunicorn. Alembic reads all migration files in backend/alembic/versions/  and
applies them in order to create the full database schema (users, documents, ocr_results,
classification_results, extraction_results, validation_results, audit_logs, workflow_history,
training_examples). This runs every time the container starts but is idempotent — if the
schema is already up to date, it completes in under a second.
Step 6 — Open the Application
What: Open your browser.
Why: The frontend Nginx container is bound to FRONTEND_PORT  (default: 80) on your host
machine. All API calls from the frontend go to /api/...  which Nginx proxies internally to
the backend container — your browser never talks to the backend directly.
If you changed FRONTEND_PORT  to e.g. 8080 :

Step 8 — EasyOCR Model Download (First OCR Request Only)
What: On the very first document you upload and process with EasyOCR, there will be a
delay of ~1–3 minutes.
Why: EasyOCR downloads its English recognition model weights (~100 MB) from the
internet on first use. The model is saved to the backend_model_cache  Docker volume
(mapped to /home/efdi  in the container). Because this volume persists across container
restarts and rebuilds, the download only happens once for the lifetime of the deployment.
Subsequent OCR calls load from the local volume and are fast.
If your machine has no internet access after setup, pre-warm the model cache before going
offline:

POSTGRES_PASSWORD  error on startup
The .env  file is missing or not in the efdi/  directory. Make sure you are running docker 
compose up  from inside the efdi/  folder (where docker-compose.yml  lives), not from
the parent folder.
Backend container keeps restarting
Common causes:
Alembic migration failure — usually a DB connection issue. Check that the
postgres  container is healthy: docker compose ps
SECRET_KEY  placeholder — if you accidentally cleared the SECRET_KEY  in .env , the
backend startup check will reject it. Regenerate: openssl rand -hex 32
EasyOCR model download fails / times out on first OCR
The model downloads from GitHub Releases / HuggingFace on first use. If your network is
slow or restricted:
Switch to OCR_DEFAULT_ENGINE=stub  in .env  and docker compose restart 
backend  to use placeholder OCR while you sort out connectivity.
Or pre-download the EasyOCR model files manually and volume-mount them — see
EasyOCR docs for model file locations.
docker compose  not found (Linux)
You have the old standalone docker-compose  (v1) instead of the Compose v2 plugin.
Install the plugin:

Architecture Reminder
No port on the backend or Postgres is exposed to your host machine by default. The only
open port is FRONTEND_PORT  (Nginx). This is intentional — the backend API is only
reachable through the frontend's Nginx proxy, and Postgres is only reachable from the
backend, both over Docker's internal bridge network.
To expose the backend API directly for debugging (e.g. to access /api/docs  Swagger UI),
uncomment the ports  block in docker-compose.yml  under the backend  service:
sudo apt-get install docker-compose-plugin   # Ubuntu/Debian
